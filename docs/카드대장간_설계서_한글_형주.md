# 카드대장간 Granite React Native 설계 전환 검토서

> 작성 기준: 2026. 08. 26  
> 대상 저장소: `bluehawhy/card-forge`  
> 검토 목적: 기존 WebView/Vite 기준 설계를 현재 Granite React Native 구현에 맞게 정정할 범위와 근거를 정의한다.

---

## 1. 문서 목적

기존 `카드대장간_설계서_한글.md`는 카드대장간의 최종 기능을 클라이언트, 서버, 공통 타입으로 분리한 좋은 목표 설계다. 그러나 클라이언트 기술을 **React + TypeScript + Vite 기반 WebView**로 가정한 시점에 작성되어, 현재 GitHub 저장소에서 실제로 사용하는 **Granite React Native + TypeScript** 구조와 일치하지 않는 부분이 있다.

이 문서는 다음 네 가지를 설명한다.

1. 현재 설계서가 무엇을 가정하고 있는지
2. 현재 저장소가 실제로 어떻게 구성되어 있는지
3. 어떤 설계를 왜 수정해야 하는지
4. 앱인토스 연결과 로컬 번들링을 유지하면서 사용할 최종 권장 구조

이 문서의 핵심 원칙은 **정상 동작하는 코드를 과거 설계서에 맞춰 이동하지 않고, 설계서를 현재 코드와 선택된 기술에 맞추는 것**이다.

---

## 2. 현재 설계서의 구조

기존 설계서는 다음과 같은 모노레포를 목표로 한다.

```text
root/
├── apps/
│   ├── client/        # React + TypeScript + Vite WebView
│   └── server/        # Node.js + NestJS
└── shared/            # 클라이언트·서버 공통 타입
```

### 2.1 기존 클라이언트 가정

```text
apps/client/
├── public/
├── src/
│   ├── assets/
│   ├── components/
│   ├── hooks/
│   ├── pages/
│   ├── stores/
│   ├── services/
│   ├── router.tsx
│   ├── App.tsx
│   └── main.tsx
├── package.json
└── vite.config.ts
```

이 구조는 브라우저에서 실행되는 일반적인 React 애플리케이션에 적합하다. `div`, `img`, `button`, CSS, React Router, Vite 번들러를 전제로 한다.

### 2.2 기존 서버 가정

```text
apps/server/src/
├── modules/
│   ├── auth/
│   ├── ads/
│   ├── pack/
│   ├── enhance/
│   ├── sell/
│   ├── exchange/
│   ├── collection/
│   └── fraud-detection/
├── common/
├── database/
├── app.module.ts
└── main.ts
```

서버가 인증, 카드팩, 강화, 판매, 교환 및 부정행위 탐지를 책임별로 나눈다는 방향은 유효하다. 다만 이 트리는 대부분 **완성 단계의 목표 구조**이며 현재 모든 모듈이 구현되어 있다는 뜻은 아니다.

## 3. 현재 GitHub 저장소의 실제 구조

현재 저장소의 클라이언트는 `apps/client`가 아니라 저장소 루트에 있다. 서버만 npm workspace인 `apps/server`에 위치한다.

```text
root/
├── public/
│   └── emulator_skin/
├── src/
│   ├── _app.tsx
│   ├── pages/
│   ├── features/user/
│   ├── services/
│   └── router.gen.ts
├── apps/
│   └── server/
│       ├── migrations/
│       └── src/
│           └── membership/
├── granite.config.ts
├── babel.config.js
├── react-native.config.js
├── require.context.ts
├── index.ts
└── package.json
```

### 3.1 현재 클라이언트 기술

현재 `package.json`과 실행 코드가 사용하는 핵심 기술은 다음과 같다.

- React 19
- React Native 0.84
- Granite React Native
- Apps in Toss React Native Framework
- TDS React Native
- TypeScript
- Jest
- Testing Library React Native
- Biome

실행 및 빌드 명령도 Vite가 아니라 Granite와 Apps in Toss CLI를 사용한다.

```text
npm run dev    → granite dev
npm run build  → ait build
```

### 3.2 현재 앱 진입과 라우팅

현재 앱은 `src/_app.tsx`에서 `AppsInToss.registerApp()`으로 등록된다. 각 화면은 `createRoute()`로 경로를 선언하며, `src/router.gen.ts`는 Granite가 자동으로 생성한다.

```text
index.ts
→ src/_app.tsx
→ AppsInToss.registerApp
→ createRoute로 등록된 화면
```

따라서 Vite의 `main.tsx`, 브라우저용 `App.tsx`, 수동 `router.tsx`는 현재 구조에 필요하지 않다.

### 3.3 현재 회원 클라이언트

```text
src/features/user/
├── domain/
├── ports/
└── infrastructure/

src/services/userService.ts
```

이 영역은 모바일 앱에서 Apps in Toss의 `getUserKeyForGame()`을 호출하고 회원 서버에 세션 생성을 요청한다. 서버의 인증 폴더와 경쟁하는 구조가 아니라, **클라이언트에서 회원 기능을 사용하는 계층**이다.

### 3.4 현재 회원 서버

```text
apps/server/src/membership/
├── membership.controller.ts
├── membership.service.ts
├── postgres-user.repository.ts
├── toss-game-user.verifier.ts
├── membership.crypto.ts
└── membership.types.ts
```

현재 서버는 다음 기능을 제공한다.

- Toss 게임 사용자 식별키의 서버 검증
- 기존 회원 조회 및 신규 회원 생성
- 기본 지갑 생성
- 세션 발급과 폐기
- 현재 회원 조회 및 프로필 변경

따라서 현재의 `membership`은 단순 로그인보다 넓은 책임을 가진다.

## 4. 수정이 필요한 설계와 근거

### 4.1 플랫폼 표기

| 구분 | 현재 설계 | 수정 설계 |
|---|---|---|
| 앱 실행 방식 | Apps in Toss WebView | Apps in Toss React Native 미니앱 |
| 클라이언트 프레임워크 | React + Vite | Granite React Native |
| UI 기본 요소 | HTML DOM과 CSS | React Native 컴포넌트와 `StyleSheet` |
| TDS | 웹용 TDS 전제 | `@toss/tds-react-native` |

**수정 근거:** 현재 의존성에 `@granite-js/react-native`, `react-native`, `@apps-in-toss/framework`, `@toss/tds-react-native`가 설치되어 있다. Vite와 웹 프레임워크는 설치되어 있지 않다.

### 4.2 클라이언트 위치

| 구분 | 현재 설계 | 수정 설계 |
|---|---|---|
| 클라이언트 위치 | `apps/client` | 저장소 루트의 `src`와 Granite 설정 파일 |
| 서버 위치 | `apps/server` | `apps/server` 유지 |

**수정 근거:** 현재 앱인토스 개발 서버, 번들 진입점, Babel 설정, 라우트 탐색 및 `ait build`가 루트 프로젝트를 기준으로 구성되어 있다. 클라이언트를 `apps/client`로 옮기면 설정 경로와 npm workspace 구성을 함께 변경해야 하므로 불필요한 장애 위험이 생긴다.

장기적으로 모든 애플리케이션을 `apps/*` 아래로 통일할 수는 있지만, 이는 문서 정정과 별개의 마이그레이션 프로젝트로 검증해야 한다.

### 4.3 화면과 라우팅

| 현재 설계 | 수정 설계 |
|---|---|
| React Router | Granite `createRoute()` |
| `router.tsx` | `router.gen.ts` 자동 생성 |
| `App.tsx` | `src/_app.tsx` |
| `main.tsx` | 루트 `index.ts`와 Granite 진입 구조 |

**수정 근거:** 현재 `src/pages/index.tsx`와 `src/pages/about.tsx`가 `createRoute()`를 사용한다. `src/router.gen.ts`에는 직접 수정 금지 안내가 있으며 Granite 라우트 타입이 자동 등록된다.

### 4.4 UI와 애니메이션

| 현재 설계 | 수정 설계 |
|---|---|
| `div`, `img`, `button` | `View`, `Image`, `Pressable`, `Text` |
| CSS | React Native `StyleSheet` |
| Framer Motion | React Native 호환 애니메이션 방식 |

**수정 근거:** React Native에는 브라우저 DOM이 없다. Framer Motion을 확정 기술로 적기보다 기본 `Animated` 또는 추후 검증된 React Native 호환 라이브러리를 선택해야 한다. 고급 애니메이션 라이브러리는 실제 도입과 앱인토스 빌드 검증 후 설계에 확정한다.

### 4.5 이미지와 사운드 자산

기존 설계의 `public/images`, `public/audio`는 웹 서버가 URL로 정적 파일을 제공한다는 인상을 준다. Granite React Native에서는 앱 번들에 포함할 이미지·사운드를 코드에서 import 또는 `require`할 수 있는 자산 구조로 관리해야 한다.

권장 목표:

```text
src/assets/
├── images/
│   ├── cards/
│   └── backgrounds/
├── audio/
├── icons/
└── fonts/
```

현재 `public/emulator_skin`은 개발 도구용 파일이므로 게임 자산과 구분한다.

**수정 근거:** React Native의 번들 자산은 브라우저의 `/images/file.png` URL 사용 방식과 다르다. 카드 작업을 시작하기 전에 실제 Granite 번들에서 이미지와 음원이 Android/iOS 모두 정상 포함되는지 작은 자산으로 검증한다.

### 4.6 상태 관리와 API 통신

기존 설계는 Zustand, TanStack Query, Axios를 확정 기술처럼 표기한다. 현재 저장소에는 이 패키지들이 설치되어 있지 않고 회원 기능은 포트·Repository·Service와 `fetch` 주입 구조를 사용한다.

수정 원칙:

- 서버 통신 경계는 현재 `features/*/ports`와 `infrastructure` 패턴을 유지한다.
- 화면용 진입점은 `services` 또는 기능별 훅으로 제공한다.
- TanStack Query는 서버 상태 캐시가 실제로 필요할 때 도입한다.
- Zustand는 여러 화면이 공유하는 UI 상태가 생길 때 도입한다.
- Axios는 필요한 기능이 명확하지 않으면 추가하지 않고 기본 `fetch`를 유지한다.

**수정 근거:** 아직 사용하지 않는 라이브러리를 설계의 필수 조건으로 만들면 의존성만 늘고 실제 코드와 문서가 다시 달라진다.

### 4.7 테스트 도구

| 현재 설계 | 수정 설계 |
|---|---|
| Vitest | Jest |
| Playwright 중심 | Testing Library React Native 중심 |

**수정 근거:** 현재 저장소에는 Jest와 `@testing-library/react-native`가 설치되어 있고 실제 회원 테스트도 Jest로 실행된다. Playwright는 브라우저 DOM 기반 UI 테스트이므로 React Native 화면의 기본 테스트 도구로 적절하지 않다. 향후 기기 수준 E2E 도구는 별도 검토한다.

### 4.8 서버 모듈 구조

기존 목표인 기능별 서버 분리는 유지할 가치가 있다. 다만 현재 코드를 바로 `modules/auth`로 옮기지 않는다.

현재:

```text
apps/server/src/membership/
```

기능이 커진 뒤의 분리 후보:

```text
apps/server/src/
├── auth/             # Toss 검증, 세션 발급·폐기
├── users/            # 회원 조회, 프로필, 상태
├── wallets/          # 기본 지갑, 잔액, 재화 원장
├── cards/            # 카드 원본과 사용자 보유 카드
├── packs/            # 카드팩 발급과 결과
├── enhancement/      # 강화 판정과 결과 기록
├── exchange/         # 결정·포인트 교환
└── fraud-detection/  # 요청 제한과 감사 기록
```

**수정 근거:** 현재 `membership`은 인증, 사용자, 지갑 생성까지 하나의 안전한 트랜잭션으로 처리한다. 구현 규모가 작은 단계에서 이름만 맞추기 위해 나누면 파일 간 이동과 의존성만 늘어난다. 실제 책임과 변경 빈도가 분리될 때 리팩터링한다.

### 4.9 공통 타입 위치

기존 설계의 루트 `shared`는 장기적으로 유효하지만 현재는 존재하지 않는다. 당장은 기능별 타입을 각 영역 내부에 둔다.

```text
현재:
src/features/user/domain
apps/server/src/membership/membership.types.ts

장기 후보:
packages/contracts
```

공통 계약 패키지는 카드·강화·팩 API가 늘어나 클라이언트와 서버의 중복 타입이 실제 문제가 될 때 도입한다. 서버가 받는 외부 데이터는 공유 TypeScript 타입과 별개로 런타임 검증해야 한다.

## 6. 기능 호출 흐름

### 6.1 앱 시작과 회원 초기화

```text
Apps in Toss가 앱 실행
→ Granite 진입점 로드
→ AppsInToss.registerApp
→ 홈 화면 생성
→ getUserKeyForGame 호출
→ 회원 서버에 세션 생성 요청
→ 서버가 Toss 식별키 검증
→ 기존 회원 조회 또는 신규 회원·기본 지갑 생성
→ 앱이 회원 세션과 공개 프로필 수신
```

클라이언트는 Toss 사용자 식별키의 진위나 회원 권한을 확정하지 않는다. 서버가 검증하고 세션을 발급한다.

### 6.2 카드 강화

```text
사용자가 강화 버튼 선택
→ Granite React Native 화면이 강화 API 요청
→ 서버가 세션과 카드 소유권 확인
→ 서버가 강화 확률과 재료 확인
→ 서버 난수로 성공·실패·파괴 확정
→ PostgreSQL 트랜잭션으로 카드와 재화 변경
→ 결과 및 판정 버전을 원장에 기록
→ 앱은 서버 결과에 맞는 애니메이션만 표시
```

강화, 카드팩 개봉, 카드 판매, 결정 및 포인트 변경은 클라이언트에서 확정하지 않는다.

### 6.3 중복 요청 방지

```text
클라이언트가 요청별 고유 requestId 전송
→ 서버가 기존 처리 여부 확인
→ 처음 받은 요청만 처리
→ 같은 requestId 재전송은 기존 결과 반환
```

사용자가 버튼을 여러 번 누르거나 네트워크가 재시도해도 보상과 포인트가 중복 지급되지 않아야 한다. 사용량 증가 시 Redis 잠금과 요청 제한을 추가하되, 최종 일관성은 PostgreSQL 제약조건과 트랜잭션으로 보장한다.

## 8. 적용 순서

### 1단계: 문서 정합성 수정

- 한글·영문 시스템 설계서와 게임 기획서의 플랫폼 표현을 통일한다.
- 현재 구현과 미래 목표를 문서에서 명확히 구분한다.

### 2단계: 첫 Granite 게임 UI 구현

- 불 속성 카드 한 장의 React Native 컴포넌트와 미리보기 화면을 구현한다.
- `View`, `Image`, `Text`, `Pressable`, `StyleSheet` 및 TDS React Native를 사용한다.
- 기존 앱 시작, 라우팅, 회원 기능에 영향을 주지 않는 독립 화면으로 검증한다.

### 3단계: 카드 도메인과 API 계약

- 카드 원본과 사용자 보유 카드 타입을 정의한다.
- 클라이언트는 표시와 요청만 담당하고 카드 발급 및 강화 결과는 서버가 결정한다.

### 4단계: 서버 게임 모듈 확장

- 카드팩, 강화, 판매, 재화 원장을 기능 단위로 추가한다.
- 요청 중복 방지와 DB 트랜잭션을 각 보상 API에 적용한다.

### 5단계: 필요해진 공통 인프라 도입

- 화면 간 서버 상태 공유가 복잡해지면 TanStack Query를 검토한다.
- 전역 UI 상태가 실제로 늘어나면 Zustand를 검토한다.
- 카드·강화 계약 중복이 커지면 `packages/contracts`를 검토한다.
- 동시 보상 처리량이 늘어나면 Redis 잠금 및 요청 제한을 확장한다.

각 기술은 설계서에 먼저 확정하지 않고, 실제 필요와 앱인토스 Android/iOS 빌드 검증을 통과한 뒤 채택한다.

## 9. 최종 결론

기존 설계서의 **클라이언트·서버 분리, 서버 권한형 게임 판정, 기능별 책임 분리, 거래 원장과 중복 지급 방지** 원칙은 유지한다.

수정해야 하는 것은 클라이언트 구현 방식이다.

```text
기존 가정
React + Vite + WebView + React Router + CSS

수정 기준
Granite React Native + Apps in Toss RN Framework
+ createRoute + React Native UI + StyleSheet
```

현재 정상 작동하는 Granite 클라이언트를 `apps/client`로 이동하거나 Vite로 다시 만드는 것은 권장하지 않는다. 저장소 루트의 클라이언트와 `apps/server`의 서버 구성을 현재 기준 구조로 확정하고, 게임 기능은 `src/features`와 `apps/server/src`에 단계적으로 추가한다.

따라서 최종 결정은 다음과 같다.

1. **코드를 과거 WebView 설계에 맞추지 않는다.**
2. **기존 설계 문서를 Granite React Native 기준으로 수정한다.**
3. **앱인토스 연결, Granite 라우팅, 로컬 번들링 구조는 유지한다.**
4. **회원 클라이언트와 회원 서버 구조는 유지한다.**
5. **첫 게임 UI는 불 속성 카드부터 독립적으로 추가한다.**
6. **새 라이브러리는 실제 필요와 빌드 검증 후 도입한다.**

이 방식이 현재 구현을 보호하면서도 카드대장간을 사용자 증가와 기능 확장에 대응할 수 있는 구조로 발전시키는 가장 낮은 위험의 경로다.
