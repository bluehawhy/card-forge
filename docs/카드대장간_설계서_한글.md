# 앱인토스 6원소 카드 강화 포인트 게임 - 시스템 코드 구조 및 디렉토리 설계서

> **작성 기준:** 2026. 08. 25  
> **기반 기획:** 앱인토스 6원소 카드강화 포인트게임 기획서 v1.0  
> **기술 스택:** React + TypeScript + Vite (Client) / Node.js + NestJS (Server) / PostgreSQL + Redis (Database)

---

## 1. 전체 프로젝트 구조 개요

본 시스템은 **앱인토스 WebView 기반 React 클라이언트**와 **NestJS 기반 백엔드 서버**, 그리고 공통 타입을 공유하는 **Monorepo / Shared Modules** 구조로 설계되었습니다.

- **클라이언트 (`apps/client`)**: 사용자 UI/UX rendering, TDS 컴포넌트, Framer Motion 연출, 보상형 광고 SDK 연동 담당
- **서버 (`apps/server`)**: 모든 확률 판정(강화/파괴/팩 개봉), PostgreSQL DB 트랜잭션, 토스 포인트 API 연동, 어뷰징 검증 담당
- **공통 (`shared`)**: Client와 Server 간 공유하는 DTO, Enum, TypeScript Interface 관리

## 3. 주요 모듈 구현 핵심 가이드라인

### 3.1. 강화 및 난수 확정 모듈 (`apps/server/src/modules/enhance`)
- **서버 단독 권한**: 성공, 일반 실패, 파괴 여부는 클라이언트에서 계산하지 않고 반드시 백엔드 서버에서 난수(Cryptographically Secure PRNG 또는 Secure Random)로 확정합니다.
- **파괴 잔재 지급**: 파괴 결과 발생 시 카드 소멸 처리와 동시에 '검은 재' 아이템 수량을 DB 트랜잭션으로 지급합니다.
- **버전 관리**: 확률표(`enhance-rate.config.ts`)는 기획 정책 변경에 맞춰 버저닝하여 로그에 판정 시점의 확률표 버전을 기록합니다.

### 3.2. 포인트 및 결정 원장 모듈 (`apps/server/src/modules/exchange`)
- **고정 환율**: `3,000 강화의 결정 = 1 토스 포인트` 규칙을 상수로 엄격히 관리합니다.
- **일일 한도 및 이월**: 하루 교환 한도(기본 3P)를 초과하는 결정은 소멸하지 않고 DB 원장 balance에 저장되어 다음 날/다음 달로 이월됩니다.
- **Idempotency (동일성 검증)**: 결제 및 포인트 교환 API는 요청 식별자(Idempotency Key)와 Redis Lock을 사용하여 중복 클릭/재전송에 따른 포인트 중복 지급을 철저히 차단합니다.

### 3.3. 어뷰징 탐지 및 원장 기록 (`apps/server/src/modules/fraud-detection`)
- 사용자 ID(토스 식별자 1:1) 기반으로 초당 요청 횟수, 비정상 강화 클릭 속도, 디바이스 교체 패턴을 감지합니다.
- 리워드 지급 관련 주요 액션은 `audit-logger.ts`를 거쳐 복구 불가능한 감사 로그로 보존됩니다.
