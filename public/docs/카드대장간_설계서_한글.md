## 1. 전체 프로젝트 구조 개요

본 시스템은 저장소 루트에서 실행되는 **Apps in Toss Granite React Native 클라이언트**와 `apps/server`의 **NestJS 백엔드 서버**로 구성합니다. 클라이언트는 화면과 사용자 입력을 담당하고, 서버는 회원 인증과 모든 게임 결과·재화 변경을 최종 확정합니다.

- **클라이언트 (`pages`, `src`)**: Granite 라우팅, React Native/TDS UI, 카드·강화 연출, Apps in Toss SDK 연동 담당
- **서버 (`apps/server`)**: 모든 확률 판정(강화/파괴/팩 개봉), PostgreSQL DB 트랜잭션, 토스 포인트 API 연동, 어뷰징 검증 담당
- **공통 계약**: 현재는 각 기능 내부 타입과 API 계약으로 관리하고, 중복이 커질 때 별도 공통 패키지 도입을 검토

## 3. 주요 모듈 구현 핵심 가이드라인

### 3.1. 강화 및 난수 확정 모듈 (`apps/server/src/enhancement`)
- **서버 단독 권한**: 성공, 일반 실패, 파괴 여부는 클라이언트에서 계산하지 않고 반드시 백엔드 서버에서 난수(Cryptographically Secure PRNG 또는 Secure Random)로 확정합니다.
- **파괴 잔재 지급**: 파괴 결과 발생 시 카드 소멸 처리와 동시에 '검은 재' 아이템 수량을 DB 트랜잭션으로 지급합니다.
- **버전 관리**: 확률표(`enhancement-rate.config.ts`)는 기획 정책 변경에 맞춰 버저닝하여 로그에 판정 시점의 확률표 버전을 기록합니다.

### 3.2. 포인트 및 결정 원장 모듈 (`apps/server/src/exchange`)
- **고정 환율**: `3,000 강화의 결정 = 1 토스 포인트` 규칙을 상수로 엄격히 관리합니다.
- **일일 한도 및 이월**: 하루 교환 한도(기본 3P)를 초과하는 결정은 소멸하지 않고 DB 원장 balance에 저장되어 다음 날/다음 달로 이월됩니다.
- **Idempotency (동일성 검증)**: 결제 및 포인트 교환 API는 요청 식별자(Idempotency Key)와 Redis Lock을 사용하여 중복 클릭/재전송에 따른 포인트 중복 지급을 철저히 차단합니다.

### 3.3. 어뷰징 탐지 및 원장 기록 (`apps/server/src/fraud-detection`)
- 사용자 ID(토스 식별자 1:1) 기반으로 초당 요청 횟수, 비정상 강화 클릭 속도, 디바이스 교체 패턴을 감지합니다.
- 리워드 지급 관련 주요 액션은 `audit-logger.ts`를 거쳐 복구 불가능한 감사 로그로 보존됩니다.
